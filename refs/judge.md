# 判断：把直觉变成能站住的断言

## 依据强度（现场判，不预设等级）

| 强度 | 长什么样 | 怎么写 |
|---|---|---|
| **强** | 追到具体实例或条文，能指出谁在哪何时说的 | 进主表，附来源 |
| **中** | 只能追到「通常这么做」，无具体出处 | 进主表，标「通行做法」 |
| **推理** | 无外部背书，但讲得出为什么 | 进主表，标「推理」 |
| **无** | 讲不出为什么 | 删 |

「推理」不是次等。有些最实的问题恰恰没有任何规范写过——比如「这段代码声称支持多机，实际只认一个端口」。这种情况比引用规范更有力，因为它不需要权威背书，它只需要你指出矛盾。

## 断言与证据必须匹配

**这是防误报的核心。** 拿静态存在性证明行为性结论，是这类评审最常见的错。

| 断言类型 | 需要什么 | 只有静态 grep 够不够 |
|---|---|---|
| 存在 X | 找到定义或调用 | 够 |
| **没有 X** | 搜过反义词与替代实现，且追到启动/初始化路径 | **不够** |
| X 起作用 | 追到调用链与副作用 | 不够 |
| X 不起作用 | 追到干扰它的路径 | 不够 |
| 性能 / 并发 / 内存 | 实测数据 | 远不够 |
| 有安全风险 | 追到可达输入到危险点的完整路径 | 远不够 |

匹配不上的，降级写「未验证（静态推断）」，不进主表。

## 反向搜索：说「没有」之前必须先搜

```
recover  stale  cleanup  ignore  fallback  default
retry  resume  restore  repair  audit  guard  hook
```

外加该领域的同义词、近义词、缩写。

**命中 0 只说明这个名字没出现**，不说明这个机制不存在。机制可能在：
- 依赖包里（看 `package.json` / `requirements.txt` / `go.mod`）
- 框架默认行为里
- 另一层（网关、反向代理、容器编排）
- 配置里（环境变量、启动参数）

## 影响面三查：下结论前

三类断言最容易翻车，翻车方式都相同——**只看了被点名的那个，没看围着它的**。

| 断言涉及 | 必查 | 教训来源 |
|---|---|---|
| **改接口 / 删字段** | 谁在调用：`grep` 前端、测试、文档、健康检查 | health 同时是前端 bootstrap，不是纯诊断面板 |
| **安全 / 暴露面** | 运行边界：绑定地址默认值、鉴权默认开关、隧道与反代、容器网络 | 默认 `HOST=127.0.0.1` 时，匿名可读不是系统级 |
| **某类缺失 / 某处多余** | 同类还有几处：全部路由、全部豁免名单、全部同类目录 | 只报 `/api/health`，漏了同样免鉴权的 `/api/admin/health` |

### 严重度怎么写

```
严重度 = 暴露概率 × 影响
```

只看「影响」会把条件性问题写成系统级。暴露概率由运行边界决定，不是由代码决定。

| 边界 | 处置 |
|---|---|
| 默认只绑回环、走隧道 | 中／条件性：写明「在 X 条件下升为系统级」 |
| 默认绑 0.0.0.0、无鉴权 | 系统级 |
| 无法确认部署形态 | 写「取决于部署形态，未验证」，不给系统级 |

## 支配判定：动它会不会牵连别的

| 问 | 结论 |
|---|---|
| 动它，有没有一个方面变差？ | 无 → **无条件做** |
| 有，哪方面？ | 逐项列出（耗时 / 体验 / 资源 / 暴露面 / 可维护性 / 交付成本） |
| 谁受损、受多少？ | 写清，不糊过去 |
| 谁裁决？ | 交给决策者，不替他选 |

**不给前沿排序，不做加权总分。** 加权求和会把隐式权重糊进一个数，让冲突消失——而那正是要被看见的东西。

## 三类判定

| 结果 | 处理 |
|---|---|
| 无一项变差 | 直接做，不必讨论 |
| 有一项变差 | 列两头代价，标出谁受损 |
| 全平 | 无收益，删 |

## 停手线

不是所有能改的都值得改。写建议前先问：

- 这个改动如果完全不做，谁会遇到什么问题？
- 答不出具体的人与场景，就是审美偏好，不进表。
