# 报告怎么写

## 骨架

```markdown
# 他山评审 · <对象> · <日期>

- 对象类：一句话说清它是什么、给谁用
- 输入路径：<路径>
- 取证时点：<日期>｜工作区状态：已提交 / 有未提交改动
- 证据来源：跑过哪些脚本、读过哪些目录
- 历史参照：上一次同对象评审｜记忆残留：<有/无>
- 自评局限：评审者与对象是否同源

## 1 空手看的怪处

（原始清单，未分组的直觉，一条一行）

## 2 参照源

| # | 来源 | 年份/版本 | 口径 | 可比 |
|---|---|---|---|---|

## 3 差距（按现场起的名字分组）

### 3.1 <组名>

| # | 场景句式 | 证据 | 影响面 | 依据 |
|---|---|---|---|---|

## 4 存疑

（依据只有推理、或讲不清的，单列）

## 5 动作（落到增删改，不落到代码）

三层的边界，越界就是抢设计师的活：

| 层 | 例 | 给不给 |
|---|---|---|
| 差距 | `.dockerignore` 排除了 `model-relay/` 却没排除 `dataset-service/` | 总是给 |
| **动作** | 在该文件 `model-relay/` 那行后加一行 `dataset-service/` | 满足三门槛才给 |
| 实现 | 改完的完整文件、完整函数 | **永不给** |

### 三门槛（全部满足）

**① 支配型**：没有一个方面变差。

有代价的动作是取舍，只给差距，交给决策者。「加令牌」不写动作——它让本地调试变难，那是别人要权衡的。

**② 观测值可预测**：写得出「改完这张命令输出变成什么」。

写不出，说明因果链没闭合。**这一条是拿错修法换来的。**

**③ 标状态**

| 状态 | 含义 | 允许 |
|---|---|---|
| `已模拟` | 本次在临时副本上跑过，观测值确实变了 | ✓ |
| `可预测` | 没跑，但改动与观测值的因果链封闭 | ✓ |
| `未验证` | 因果链不闭合 | **不许写动作** |

### 反例（真实发生过）

| 项 | 内容 |
|---|---|
| 差距 | `jiaoshu.service` 里 Node 路径写死了版本号 |
| 给的动作 | `Environment=NODE_BIN=...` + `ExecStart=$NODE_BIN server.mjs` |
| 为什么错 | systemd 不在可执行文件路径里展开环境变量 |
| 后果 | 照做**完全不生效**，比不给更糟——对方踩坑后不再信这份报告 |

判据一句话：**写不出「改完这条命令会输出什么」，就只写差距。**

### 动作怎么写

| 要素 | 要求 |
|---|---|
| 位置 | 文件 + 段落（不用绝对行号，行号会漂） |
| 动作 | 加 / 删 / 改什么，一句话 |
| 观测值 | 改完跑什么命令、期望变成什么 |
| 状态 | 已模拟 / 可预测 |

```markdown
| # | 位置 | 动作 | 观测值变化 | 状态 |
|---|---|---|---|---|
| 1 | `.dockerignore` 的 `model-relay/` 后 | 加一行 `dataset-service/` | `grep -c dataset-service .dockerignore`：0 → 1 | 可预测 |
| 2 | — | （只给差距：补 compose service 取决于部署形态） | 不可预测 | — |
```

第 2 行那种，老实写「不可预测」，降回差距层。

## 6 合起来像什么（推测，未验证）

（把差距串成一句判断，注明是怎么串的，并给出证实它需要问的 2-3 个问题）

## 7 建议

| # | 改法 | 影响 | 验后值 |
|---|---|---|---|

## 8 未查范围

| 项 | 原因 |
|---|---|

## 9 自检
```

## 验后值必须是跑出来的

**这一节是拿误报换来的。**

```bash
$ grep -rn "dataset-service\|model-relay" docker-compose.yml Dockerfile deploy/ | wc -l
1
```

贴的是**实际输出**，不是「当前 1」。

| 不写 | 写 |
|---|---|
| `# 当前 0` | `# 1（本次实跑）` |
| `# 当前 N`（没跑） | `# 未跑，估 3——未验证` |

「未跑，估」是诚实的，可以接受；「当前 0」而没跑，是最坏的一种——它看起来像证据。

## 范围句必须等于取证范围

写「整个仓库」「全部」「没有任何」之前，先列出扫过的路径。

| 说了 | 就必须扫 |
|---|---|
| 整个仓库 | 代码目录 + 所有 `README.md` + `deploy/` + 配置文件 |
| 没有任何配置 | 区分「没有机器可读配置」与「没有文档说明」——两者严重度差一个量级 |
| 全部端点 | 全部路由 + 全部鉴权豁免名单 |

**扫了三个路径就说「整个仓库」，是这一轮最大的失误。**

## 每条差距的写法

> 当【触发条件】时，当前【事实 · `文件:行`】，差距【可判定差值】。

三要素缺一不可：**条件、事实、差值**。

| 差 | 好 |
|---|---|
| 「性能有优化空间」 | 「当首屏加载时，当前 JS 158 KB 未压缩，gzip 后约 50 KB，多传 108 KB」 |
| 「建议统一设计规范」 | 「当前两套色板各存 85 与 59 个色值，同一语义两处不同色」 |

## 影响必须正向

```
<结果类>：<现状> → <之后>
```

例：`看不懂：18 种字号 → 6 种，同一层级只有一种大小`

写不出正面影响的，这条不进表。**写不出不是因为它不重要，是因为还没想清改完会怎样。**

## 推测区怎么写

单独一节，**只用一句判断**，后面跟证据链与验证问法。

```markdown
## 合起来像什么（推测，未验证）

> 四条部署问题叠在一起，像在说这个项目的部署依赖个人经验，没有沉淀成可复制的流程。

**凭什么这么说**：缺两个 service（没人负责完整部署）+ 七个启动脚本（每次现写）+ 路径写死版本号（机器长期不动）+ host 网络（图省事）。

**怎么证实**：问三个问题——另外两个服务谁起的？上次部署是谁做的？换个人能不能独立部署？

**如果是错的**：如果部署另有脚本未入仓、或由平台统一托管，这个推测作废，四条差距仍然成立。
```

三条规矩：

| 规矩 | 为什么 |
|---|---|
| 一句判断，不展开成三条 | 展开就成了编故事 |
| 必须给验证问法 | 没有验证路径的推测是猜 |
| 必须写「如果错了会怎样」 | 让自己先想好退路 |

**推测区永远不进差距表，不进建议，不做优先级。** 它是给读者的线索，不是结论。

**不许用推测反推差距成立。** 写「所以那几条差距仍然成立」，等于把假设当支撑——四条里两条被复核推翻了，这句话会让另外两条一起失真。

## 存疑怎么写

单列，不进主表，也不删。

```markdown
| # | 疑点 | 为什么存疑 | 下一步 |
|---|---|---|---|
| 1 | 列表分页逻辑三处实现 | 三处代码都读过，但不确定是否互斥 | 需在浏览器里对比三处触发条件 |
```

存疑区不是垃圾桶——下一轮可能追到依据，升进主表。

## 建议栏：修法要先验证

给修法前确认它在目标运行时成立（`Environment=NODE_BIN` 放进 `ExecStart` 是可执行路径，systemd 不展开它）。
不确定时给两种写法并标「未验证」。**给一个错修法比不给更糟**——对方照做会踩坑，然后不再信这份报告。

## 语言

| 不写 | 写 |
|---|---|
| 体验差 | 无加载态，点击后 0 反馈 |
| 不够健壮 | 网络异常时无重试，请求直接失败 |
| 建议优化 | 当前 X 是 A，参照 B，差 C |
| 业界最佳实践 | 具体来源，或自己论证 |

- **说现象不说评价。** 「加载态缺失」是现象，「体验差」是评价。
- **写差距不写建议。** 建议是愿景，差距是事实。
- **零内部术语。** 换个人（不懂这个项目）能看懂。
- **不用「我们认为」。** 要么有来源，要么是自己论证，都要标清是哪种。

## 自检

- [ ] 每条有 `文件:行` 或明确来源
- [ ] 没有「最佳实践」「一般来说」这类无主语的词
- [ ] 每个「当前值」贴的是本次命令输出，不是推算
- [ ] 自检时**复跑了至少两条**数字，而不是只看格式
- [ ] 绝对句（整个／全部／没有）的范围已核，扫过 README 与 deploy
- [ ] 影响写成「现状 → 之后」
- [ ] 每条动作过了三门槛，或已降回差距
- [ ] 动作的状态标了「已模拟 / 可预测」，没有「未验证」的动作
- [ ] 存疑区非空或有明确说明
- [ ] 未查范围写了
- [ ] 误报率已记进台账
- [ ] 换个人能看懂（术语已清）
- [ ] 没有一条是「规范没写但我看着不对」却没标「推理」的
