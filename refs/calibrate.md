# 自校：把误报变成教训

## 算法

```
误报率 = (完全误报 + 0.5 × 半误报) / 总条数
精确率 = 1 − 误报率
```

每轮报数，记进 `objects/ledger.jsonl`。

**精确率与收敛率分开报，不相乘、不加权。** 收敛率高但精确率低，说明建议有效但噪声多；反过来说明稳但推不动。

## 五种典型误报（来自真实批次）

### 1 拿静态存在性证明行为性结论

`grep` 无匹配就写「没有 X」。实际 X 在初始化路径里、在依赖包里、在框架默认行为里。

**教训**：断言缺失前，追到启动/初始化路径。

### 2 只搜一个名字

搜 `checkpoint` 无果，判「无持久化」。实际能力叫 `pi-durable`，在依赖包里。

**教训**：同义词、近义词、缩写、依赖包名一起搜。

### 3 把产品决定当缺陷

判「两套鉴权入口是缺陷」。实际是产品有意区分演示与真实。

**教训**：看着冗余的，先问是不是有意的。

### 4 口径错

拿未压缩体积比 gzip 预算，判「超 3 倍」，实际合规。

**教训**：比之前先对齐口径。

### 5 只看源码不看依赖

「没有重试机制」——重试在 HTTP 客户端库里默认开着。

**教训**：先看依赖清单，再看源码。

## 样本格式

`calibration/<对象类>-<日期>.jsonl`，每行一条：

```json
{"claim":"原报告里的断言","verdict":"false_positive|partial|not_a_defect",
 "why":"为什么错","lesson":"下次怎么做","assert_type":"行为|存在|缺失|性能"}
```

| 字段 | 要求 |
|---|---|
| `claim` | 引用原话，不改写 |
| `verdict` | 三选一；`not_a_defect` 不进误报率分子 |
| `why` | 说清事实是什么，不写「沟通有误」 |
| `lesson` | 可操作的检查动作，不是「要更小心」 |
| `assert_type` | 用于统计哪类断言最容易错 |

## 用法

**开场读 5 条**，优先读同 `assert_type` 的。

读到与自己当前要下的断言同型的，先自查一遍再写进报告。

## 什么不算误报

| 情况 | 为什么不算 |
|---|---|
| 对方承认但暂不修 | 差距成立，只是没排期 |
| 判据对但验后值写错 | 是表述问题，改表述 |
| 产品后来改了设计 | 当时确实成立 |

这三种记「已确认」，不进误报率。**把「对方不认同」当误报，会让自己只报安全的话。**

## 对不上的时候

对方说「你不懂业务」。处理顺序：

1. 找出他对的那部分事实（通常有）
2. 承认这部分，改报告
3. 剩下的部分重新给证据，或降为存疑

**不要因为被质疑就整体撤回，也不要因为被质疑就加倍防守。** 逐条对事实。
