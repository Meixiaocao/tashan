# `skill` 类 · 专属取证

配合 `common.md` 的 G1–G7 与"声明≠实现核查表"使用。

## C1 触发精度

1. 读 description：写的是"做什么 + 何时用"吗？有没有只说做什么、不说何时用。
2. 建两组样例：
   - **正例** 5 条：使用者真会说的话（口语、错别字、口语化简称）。
   - **反例** 5 条：字面相近但该由别的技能处理的说法。
3. 与同目录其他技能的触发词做交集：列出重叠词，标注哪一方更该命中。
4. 触发方式：自动（靠 description 匹配）还是需点名；误触发代价（加载无用上下文 / 抢了别的技能的活）。
5. 若有条件，实际跑一轮正例，记录是否自动加载。

**合格证据**：description 的 `文件:行`、重叠词在两份文件中的行号、实测加载记录。

## C2 载荷与冲突

1. 载荷：主文件行数/字节数；被引用文件是否每次必读（若是，等于一个大文件，拆分只是增加往返）。
2. 结构：路由是否让"只读所需部分"真的成立（分文件 + 明确指针 + 触发条件）。
3. 冲突：技能指令与宿主既有规则是否矛盾；矛盾处逐条列出，判断哪一方不可满足。
4. 出口：完成态可判定吗（检查清单 / 产出物形态）；失败态有退路吗。
5. 脚本：有无可执行脚本；脚本是否只读；脚本失败时技能是否还有出路。

**合格证据**：`wc -l` 数值、引用指针的行号、矛盾两侧的原文行号、缺退路的流程步骤行号。

## 技能类常见假象

| 假象 | 怎么破 |
|---|---|
| 拆了引用文件显得专业 | 算一下是否每次全读，全读则拆分是负收益 |
| 有检查清单 | 看清单项是否可判定，有无"尽量""注意" |
| 描述了能力 | 找对应脚本或流程步骤，找不到即未落地 |
| 写了机制名 | 找触发条件与消费者：分支跑不到、产出没人读，都等于没做 |
| 触发词很多 | 词越多误触发越多，看反例是否被覆盖 |
